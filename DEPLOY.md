# Deploying to Render (single service, existing Postgres over Tailscale)

This repo deploys as **one Render web service** — a Docker container that
builds the React frontend and serves it, together with the Django API,
from a single gunicorn process. One service = one URL.

Your Postgres database (`VetriOSDB`, managed via pgAdmin 4) stays exactly
where it is — reachable over Tailscale — instead of creating a new
database on Render. The container joins your Tailscale network on boot
and relays its DB connection through it. See `Dockerfile` and
`backend/docker/entrypoint.sh`/`backend/docker/tailscale_pg_proxy.py` for
how that works.

**Important:** this makes your deployed app's uptime depend on the
Tailscale-connected machine hosting Postgres staying on and reachable.
If that machine is off, the deployed app can't reach its database.

## 1. Generate a Tailscale auth key

1. Go to <https://login.tailscale.com/admin/settings/keys> (your Tailscale account).
2. Generate a new auth key:
   - **Reusable**: on (Render may recreate the container on redeploys/restarts)
   - **Ephemeral**: on (so old dead nodes from past deploys don't pile up in your tailnet device list)
   - Expiry: your choice (90 days is Tailscale's default; you'll need to regenerate and update the Render env var when it expires)
3. Copy the generated key (starts with `tskey-auth-...`) — you'll paste it into Render in step 3.

## 2. Find your Postgres machine's Tailscale IP

In a terminal on the machine running Postgres:

```bash
tailscale ip -4
```

This should match (or replace) the `DB_HOST` value already in your
`backend/.env` (`100.94.127.20` as of this repo's `.env.sample`).

## 3. Create the Render service

1. Push this branch (with `Dockerfile`, `render.yaml`, `DEPLOY.md`) to GitHub if you haven't already.
2. In Render: **New → Blueprint**, pick this repo. Render reads `render.yaml` and proposes one web service (`vetrios-backup`) on the **free** plan (`plan: free` in `render.yaml` — no card needed).

   Free-tier trade-off: the service spins down after ~15 minutes of no
   traffic and cold-starts (including rejoining Tailscale) on the next
   request, which takes it 30-60 seconds to respond. Fine for testing;
   if you want it always-on and instant, change `plan: free` to
   `plan: starter` in `render.yaml` (paid, ~$7/mo) before creating the
   Blueprint.
3. Before/after creation, fill in every environment variable marked `sync: false` in `render.yaml`, in the Render dashboard's Environment tab:

   | Key | Value |
   |---|---|
   | `ALLOWED_HOSTS` | your Render URL's hostname, e.g. `vetrios-backup.onrender.com` |
   | `CSRF_TRUSTED_ORIGINS` | `https://vetrios-backup.onrender.com` |
   | `TAILSCALE_AUTHKEY` | the key from step 1 |
   | `TAILSCALE_DB_HOST` | the Tailscale IP from step 2 |
   | `DB_PASSWORD` | your `vetri_app_role` Postgres password |
   | `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | from your Cloudinary account |
   | `GROQ_API_KEY` | your Groq key |
   | `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` | your default Gmail account |
   | `OUTLOOK_EMAIL_HOST_USER`, `OUTLOOK_EMAIL_HOST_PASSWORD` | the Outlook/O365 account for module_07_email |

   `SECRET_KEY` is auto-generated by Render (`generateValue: true`). Everything else without `sync: false` already has a value in `render.yaml`.

4. Deploy. Watch the build logs — the first build compiles the frontend and installs Python deps, so it'll take a few minutes.

## 4. Verify it actually works

Render's health check (`/`) only confirms the app is *up* — it doesn't
touch the database, so a green health check does **not** mean the
Tailscale relay is working. After deploy:

1. Open the Render service's **Logs** tab and look for:
   ```
   [entrypoint] tailscale status:
   [entrypoint] relay is up.
   ```
   If `tailscale up` fails or times out, the container will crash-loop —
   check the log output right above that for the actual Tailscale error
   (commonly: wrong/expired auth key, or your tailnet's ACL policy
   blocking the new node from reaching the DB host).
2. Open the deployed URL and try logging in with a real account. A
   successful login exercises the full path: gunicorn → Django →
   relay → SOCKS5 → Tailscale → Postgres.

## Known limitation

The DOCX mail-merge → PDF export (Word/COM automation, `docx2pdf`) only
works on Windows and is disabled on this Linux deployment — it now
raises a clear error instead of crashing the app if someone hits that
specific export path. Everything else (HTML/Markdown → PDF via
`xhtml2pdf`, and all other features) is unaffected.

## Redeploying

Every push to the branch Render is watching triggers a new build/deploy
automatically. Each new container gets a fresh Tailscale node identity
(ephemeral key), joins the tailnet again, and starts up the same way.
